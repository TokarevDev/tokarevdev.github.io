Engineering operating system

Architecture is useful only when it makes change safer.

The common thread across both projects is controlled change: clear dependency ownership, explicit lifecycle, data at the boundary, bounded runtime work, and evidence that systems behave as designed.

Architecture

Explicit composition

Domain-focused composition roots, constructor injection, interface boundaries, Assembly Definitions, and named gameplay stages replace hidden scene dependencies.

Runtime

Predictable hot paths

Cached references, pooled entities, NonAlloc-aware physics choices, immutable input snapshots, and allocation-conscious loops keep frame work observable.

Lifecycle

Ownership through teardown

Subscriptions, async operations, platform services, registration, rollback, pool return, and scene transitions have symmetric ownership and failure paths.

Data

Configuration at the boundary

ScriptableObjects and validated JSON keep balance out of runtime orchestration, with null, duplicate, unknown, and required-key checks before gameplay starts.

Validation

Evidence over intuition

Profiler inspection, deterministic simulations, repeatable scenarios, public code maps, and playable builds make architectural claims inspectable.

Delivery

Platform-aware completion

Android and Windows build preparation, responsive UGUI, platform input strategies, analytics boundaries, ads isolation, debugging, and release checks are part of the system.
