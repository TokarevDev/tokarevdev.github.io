Architecture & delivery case · Unity 2022 LTS

2D Asteroids Survival

A playable survival game that demonstrates how I structure a compact Unity project: stable contracts at the center, Zenject composition at scene boundaries, gameplay state outside UI, and lifecycle-safe navigation.

Architecture map

Dependencies point toward small, stable contracts.

Assembly Definitions make the direction visible in the project structure. Unity-specific implementations stay in Infrastructure, Gameplay, and UI; shared scene and input contracts live in Core.

Key engineering decisions

Small boundaries with a concrete reason to exist.

Scene composition with Zenject

Infrastructure, gameplay, and UI installers describe bindings only. Services receive dependencies through injection instead of resolving them from a global container.

Assembly-level dependency direction

Core exposes narrow contracts. Infrastructure implements input and scene loading, while Gameplay and UI depend on the contracts they need.

Session state owns game-over rules

GameSession responds to PlayerDiedSignal, prevents repeated termination, and restores time scale during teardown. The player and UI do not coordinate the session directly.

MVVM-style game-over flow

GameOverViewModel owns state and navigation commands; GameOverView only binds buttons and presentation. Event subscriptions are symmetric across enable and disable.

Input behind a lifecycle contract

InputReader implements IInputReader plus Zenject initialization and disposal. Generated Input Actions are enabled and released by the same owner.

Guarded asynchronous navigation

UniTask scene transitions disable repeated actions, restore interactability on failure, and keep scene names inside the infrastructure adapter.

Runtime and maintainability

Unity components stay focused on engine-facing work.

The project uses serialized references, setup-time validation, cached dependencies, and plain C# state where a MonoBehaviour is unnecessary.

Plain C# domain state

Health validates initialization, owns damage rules, and publishes changes without scene lookup or Unity lifecycle coupling.

Authored configuration

Asteroid health, movement speed, sprite, and scale live in ScriptableObject data rather than being spread across runtime code.

Predictable references

Required component and Inspector references are validated during setup; frequently used dependencies are cached before gameplay begins.

Review and delivery

The project can be inspected as code and played as a build.

The public repository contains the full Unity project and setup notes. Gameplay is available as video, a Windows build, and an Android APK.

Gameplay scope

Ship movement, screen wrapping, shooting, asteroid spawning, damage, lives, session end, restart, and main-menu navigation.
